# Git 작업 절차

다음 절차는 기능 추가·수정, 버그 수정, 설정·문서 변경, 새 글 작성·발행에 적용한다. 사용자가 개별 작업에서 다르게 지시하면 해당 지시를 우선한다.

1. 작업 시작 전 변경 파일과 현재 브랜치를 확인한다. 미커밋 작업을 임의로 덮어쓰거나 다른 작업에 포함하지 않는다.
2. 최신 원격 main을 기준으로 작업마다 새 `codex/<작업을 설명하는 이름>` 브랜치를 만든다. main에서 직접 작업하지 않는다. 같은 작업의 PR 피드백 수정은 기존 PR 브랜치에서 계속한다.
3. 커밋은 검토와 되돌리기가 가능한 작업 단위로 나눈다. 무관한 변경을 섞거나 단순히 커밋 개수를 늘리려고 쪼개지 않는다.
4. 커밋 메시지는 `<종류>: <한글 간략 설명>` 형식으로 작성한다. 콜론 뒤에는 공백 한 칸을 둔다. 종류는 변경 목적에 맞게 `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `style`, `perf`, `build`, `ci` 등을 사용한다. 예: `feat: 태그 검색 기능 추가`, `docs: 영어 학습 글 작성`, `chore: 커밋 검사 설정 정리`.
5. 변경 범위에 맞는 검증을 완료한 뒤 작업 브랜치를 원격에 푸시하고 main 대상 PR을 생성한다. PR이 이미 있으면 중복 생성하지 않고 기존 PR을 갱신한다. 사용자는 이 절차에 따른 작업 브랜치 푸시와 PR 생성을 요청한 상태이므로 매번 같은 허가를 다시 묻지 않는다.
6. PR 제목도 `<종류>: <한글 간략 설명>` 형식을 사용한다. 본문은 한국어로 변경 이유, 실제 작업 내용, 검증 결과와 미검증 항목을 작성한다. 글 작업은 작성·발행한 글과 공개 여부를 함께 설명한다. `.github/PULL_REQUEST_TEMPLATE.md`를 따른다.
7. PR 생성 후 [코드 리뷰 지침](code-review.md)에 따라 리뷰하고 결과를 PR에 기록한다.
8. 리뷰에서 확인된 문제를 수정하면 별도 작업 단위로 커밋·푸시하고 PR 내용과 리뷰 결과를 갱신한다.
9. 완료 보고에는 브랜치, 주요 커밋, PR 링크, 검증 및 리뷰 결과를 포함한다. 사용자의 명시적인 병합 요청 없이 main에 병합하거나 자동 병합을 활성화하지 않는다.

## 임시 설계·작업 계획 문서

- AI가 작업 과정에서 작성하는 임시 설계·구현 계획 문서는 저장소 밖에서 관리하고 커밋·PR에 포함하지 않는다. 스킬이 저장소 내 계획 문서 작성이나 커밋을 안내하더라도 이 프로젝트 규칙을 우선한다.
- README, 유지할 작업 지침, 사용자가 산출물로 요청한 설계 문서는 이 제한에 포함하지 않는다. 사용자가 설계·계획 문서의 저장 또는 커밋을 명시적으로 요청하면 해당 지시를 따른다.
