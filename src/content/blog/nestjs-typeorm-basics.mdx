## 1. 배열에 저장하던 게시글을 DB로 옮기는 이유

앞선 게시판 실습에서는 Service 내부의 배열에 게시글을 저장했습니다.

```ts
private boards: Board[] = [];
```

배열은 데이터 흐름을 익히기에는 간단하지만, 서버 프로세스를 종료하면 저장된 게시글도 사라집니다. 게시글을 서버 재시작 후에도 보관하려면 데이터를 지속적으로 저장할 장소가 필요합니다. 이번 실습에서는 그 역할로 PostgreSQL을 사용합니다.

데이터베이스를 도입하면서 TypeORM, 엔티티, 리포지토리도 함께 등장했습니다. 각각이 무엇을 담당하는지 구분하면 설정 코드를 따라 쓰는 것에서 나아가 데이터 저장 구조를 이해할 수 있습니다.

현재 실습은 DB 연결 설정과 엔티티·리포지토리 클래스를 작성한 단계입니다. Service는 아직 배열을 사용하고 있으므로, 게시글 생성 API가 PostgreSQL에 저장하는 단계까지 완성된 것은 아닙니다.

## 2. PostgreSQL과 TypeORM은 어떤 관계일까?

**PostgreSQL은 실제 데이터를 저장하고 조회하는 관계형 데이터베이스 관리 시스템입니다.** 게시글을 테이블에 저장한다면 각 게시글은 하나의 행, 제목과 내용 같은 항목은 컬럼으로 표현할 수 있습니다.

| id  | title     | description             | status |
| --- | --------- | ----------------------- | ------ |
| 1   | 첫 게시글 | NestJS 학습 기록입니다. | PUBLIC |

**TypeORM은 TypeScript의 객체와 데이터베이스의 테이블을 연결하는 ORM입니다.** ORM은 Object-Relational Mapping의 약자로, 객체와 관계형 데이터 사이의 매핑을 뜻합니다.

예를 들어 TypeORM의 리포지토리에서 조회 메서드를 호출하면, TypeORM이 SQL 실행과 결과를 객체로 변환하는 작업을 처리합니다. PostgreSQL은 그 SQL을 받아 실제 데이터를 조회합니다. 두 도구는 서로 다른 역할을 담당합니다.

프로젝트에 설치한 패키지도 역할을 나눠 볼 수 있습니다.

| 패키지            | 역할                                              |
| ----------------- | ------------------------------------------------- |
| `typeorm`         | 엔티티 매핑과 데이터 조회·저장 기능 제공          |
| `@nestjs/typeorm` | TypeORM을 NestJS의 모듈과 의존성 주입 구조에 통합 |
| `pg`              | Node.js에서 PostgreSQL과 통신하는 드라이버        |

## 3. 엔티티는 테이블과 객체의 연결 규칙이다

실습에서 작성한 `Board` 엔티티의 핵심은 다음과 같습니다. 아래 예제는 기본 자동 증가 키에 맞춰 `id`를 `number`로 표현했습니다.

```ts
import { BaseEntity, Column, Entity, PrimaryGeneratedColumn } from 'typeorm';
import type { BoardStatus } from './board.model.js';

@Entity()
export class Board extends BaseEntity {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  title: string;

  @Column()
  description: string;

  @Column()
  status: BoardStatus;
}
```

`@Entity()`는 이 클래스가 DB 테이블에 매핑되는 엔티티임을 표시합니다. `@Column()`은 해당 속성을 테이블의 컬럼에 매핑합니다. `@PrimaryGeneratedColumn()`은 값을 자동 생성하는 기본 키 컬럼을 정의합니다. 기본 키는 각 행을 구분하는 식별자입니다.

엔티티 클래스는 매핑 정의이고, 그 인스턴스는 게시글 한 건의 데이터를 담을 수 있습니다. 다만 **객체를 생성하는 것과 DB에 저장하는 것은 별개의 작업**입니다. 엔티티를 작성했다고 게시글이 자동 저장되지는 않습니다.

기존 `board.model.ts`의 인터페이스와도 차이가 있습니다. 인터페이스는 TypeScript 타입 검사에 사용되고 실행 시점에는 제거됩니다. 엔티티는 클래스와 데코레이터를 통해 TypeORM이 실행 시점에 사용할 매핑 정보를 제공합니다.

DTO가 요청에서 전달받을 데이터의 형태를 표현한다면, 엔티티는 DB에 저장할 데이터의 구조와 매핑을 표현합니다. 비슷한 필드가 있더라도 목적이 다릅니다.

`BaseEntity`는 엔티티 자체에서 조회·저장 메서드를 사용할 수 있도록 지원하는 기반 클래스입니다. 리포지토리 방식으로 데이터를 다룰 때 반드시 상속해야 하는 것은 아닙니다. 엔티티를 정의하는 핵심은 `@Entity()`와 컬럼 매핑입니다.

## 4. 리포지토리는 특정 엔티티의 데이터를 다룬다

엔티티가 저장할 데이터의 구조를 정의한다면, **리포지토리는 그 엔티티의 데이터를 조회하고 저장하는 기능을 제공합니다.**

실습에서는 다음처럼 클래스를 작성했습니다.

```ts
import { Injectable } from '@nestjs/common';
import { DataSource, Repository } from 'typeorm';
import { Board } from './board.entity.js';

@Injectable()
export class BoardRepository extends Repository<Board> {
  constructor(private dataSource: DataSource) {
    super(Board, dataSource.createEntityManager());
  }
}
```

코드를 나누어 보면 다음과 같습니다.

- `Repository<Board>`: `Board` 엔티티를 대상으로 하는 TypeORM 리포지토리를 상속합니다.
- `DataSource`: DB 연결 설정과 연결 풀, 엔티티 메타데이터 등을 관리하는 객체입니다.
- `createEntityManager()`: 해당 DataSource에 연결된 EntityManager를 만듭니다. EntityManager는 여러 엔티티의 DB 작업을 처리할 수 있습니다.
- `super(Board, ...)`: 부모인 `Repository`에 대상 엔티티와 EntityManager를 전달합니다.
- `@Injectable()`: NestJS의 의존성 주입에 사용할 클래스임을 표시합니다. 실제 주입에는 모듈의 Provider 등록도 필요합니다.

현재 클래스 본문에는 조회·저장 메서드를 직접 작성하지 않았지만, 부모 클래스의 `find()`와 `save()` 같은 메서드를 사용할 수 있습니다. 커스텀 리포지토리 클래스를 만들지 않고 TypeORM이 제공하는 기본 리포지토리를 사용할 수도 있습니다.

아래는 **초기화된 DataSource에 Board 엔티티가 등록되어 있다고 가정한 개념 예제**입니다. 현재 Service에 적용한 코드는 아닙니다.

```ts
const boardRepository = dataSource.getRepository(Board);
const boards = await boardRepository.find();
```

`find()`는 게시글을 조회하고 결과를 `Promise`로 반환합니다. 배열을 즉시 반환하던 방식과 달리 DB 작업이 완료되기를 기다려야 하므로 `await`를 사용합니다.

## 5. 모듈 설정은 무엇을 연결할까?

루트 모듈에서 사용한 `TypeOrmModule.forRoot(typeOrmConfig)`는 DB 연결과 TypeORM의 기본 설정을 구성하는 부분입니다.

설정에 있는 `type: 'postgres'`는 사용할 DB 종류를, `host`와 `port`는 접속할 위치를, `database`는 접속할 DB 이름을 나타냅니다. `entities`에는 TypeORM이 사용할 엔티티를 등록합니다.

기능 모듈에서 사용하는 `forFeature()`는 해당 모듈에서 사용할 엔티티의 리포지토리를 등록하는 역할입니다. 기본 리포지토리를 사용하는 형태는 다음과 같습니다.

```ts
TypeOrmModule.forFeature([Board])
```

여기에는 엔티티인 `Board`를 전달합니다. 실습의 커스텀 클래스인 `BoardRepository`를 전달하는 것과는 구분해야 합니다. 커스텀 리포지토리를 주입해서 사용하려면 별도의 Provider 등록이 필요합니다.

이 글에서는 등록과 주입을 완성하는 코드까지 확장하지 않고, **DB 연결 설정과 기능 모듈의 리포지토리 등록이 서로 다른 역할이라는 점**까지 정리합니다.

## 6. 현재 코드에서 이해할 데이터 흐름

현재 게시글 생성의 흐름은 다음과 같습니다.

```text
요청 → Controller → Service → 배열에 저장
```

앞으로 Service에서 리포지토리를 사용하도록 연결하면, 저장 흐름을 다음처럼 바꿀 수 있습니다.

```text
요청 → Controller → Service → Repository → PostgreSQL
```

이때 TypeORM은 엔티티의 매핑 정보를 이용해 리포지토리의 DB 작업을 처리합니다. 엔티티는 요청이 반드시 통과하는 실행 단계라기보다, 객체와 테이블을 연결하는 규칙으로 이해하는 편이 정확합니다.

현재 단계에서는 PostgreSQL이라는 저장소를 선택하고, TypeORM으로 사용할 데이터 구조와 접근 수단을 준비했습니다. Service에서 실제 조회·저장을 호출하는 작업은 그다음 단계입니다.

## 7. 학습 코드에서 주의할 점

실습 코드의 `id: string` 선언과 기본 `@PrimaryGeneratedColumn()`은 구분해서 이해해야 합니다. 기본 자동 증가 키는 숫자이므로 이 글에서는 `id: number`로 표현했습니다. UUID 문자열을 사용하려면 `@PrimaryGeneratedColumn('uuid')`처럼 생성 전략도 맞춰야 합니다.

또한 `status: BoardStatus`라는 TypeScript 타입만으로 DB에 허용할 상태값을 제한하는 제약 조건이 만들어지지는 않습니다. 요청 검증과 DB 제약 조건은 별도로 설계해야 합니다.

설정의 `synchronize: true`는 엔티티에 맞춰 DB 스키마를 자동 동기화하는 옵션입니다. 학습 과정에서는 편리하지만, 운영 환경에서는 데이터 손실 위험 때문에 사용하지 않아야 합니다. 접속 비밀번호도 글에 복사하거나 저장소에 하드코딩하지 않고 환경변수 등으로 관리해야 합니다.

이 프로젝트는 ESM을 사용하므로 설정 예제의 `__dirname`도 그대로 사용할 수 없습니다. 경로 표현은 프로젝트의 실행 방식에 맞게 확인해야 합니다. 엔티티와 리포지토리를 작성했다는 사실만으로 DB 연결과 저장 동작이 검증된 것은 아닙니다.
