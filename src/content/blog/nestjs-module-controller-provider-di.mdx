오늘은 NestJS의 기본 구성 요소인 Module, Controller, Provider와 의존성 주입을 공부했습니다. 각각의 역할을 나누고, 필요한 객체를 연결하는 방법을 배웠습니다.

함께 사용하는 개념들이라 처음에는 경계가 헷갈릴 수 있습니다. 각 요소가 무엇을 담당하고 어떻게 연결되는지 복습하며 정리해 보겠습니다.

## 1. NestJS의 기본 구성 요소

게시글 목록을 조회하는 기능을 만든다고 생각해 보겠습니다. 요청을 받는 부분, 게시글을 조회하는 부분, 이 구성 요소들을 묶는 부분으로 역할을 나눌 수 있습니다.

| 개념           | 역할                                                                   |
| -------------- | ---------------------------------------------------------------------- |
| **Module**     | 관련 Controller와 Provider를 묶고 사용 관계를 정의합니다.              |
| **Controller** | 요청을 받아 처리할 메서드와 연결하고 응답을 반환합니다.                |
| **Provider**   | 다른 구성 요소에 주입해 사용할 수 있도록 NestJS에 등록하는 대상입니다. |
| **DI**         | 필요한 의존성을 직접 생성하는 대신 외부에서 전달받는 방식입니다.       |

Service는 실제 로직을 담당할 때 흔히 사용하는 클래스이며, 대표적인 Provider입니다.

## 2. Module이란?

Module은 관련된 구성 요소를 하나의 단위로 묶는 역할을 합니다.

게시글 기능이라면 게시글 Controller와 Service를 하나의 Module에서 관리할 수 있습니다.

```ts
@Module({
  controllers: [BoardsController],
  providers: [BoardsService],
})
export class BoardsModule {}
```

이 코드는 `BoardsController`와 `BoardsService`가 이 모듈에 속한다는 것을 NestJS에 알려줍니다.

`@Module()`에는 다음과 같은 항목을 설정할 수 있습니다.

| 항목          | 역할                                                                |
| ------------- | ------------------------------------------------------------------- |
| `controllers` | 이 모듈에서 사용할 Controller를 등록합니다.                         |
| `providers`   | 이 모듈에서 사용할 Provider를 등록합니다.                           |
| `imports`     | 다른 모듈이 공개한 Provider를 사용하기 위해 해당 모듈을 가져옵니다. |
| `exports`     | 다른 모듈에서 사용할 수 있도록 Provider 등을 공개합니다.            |

예를 들어 다른 모듈에서도 게시글 Service가 필요하다면, 게시글 모듈에서 Service를 공개하고 사용하는 쪽에서 게시글 모듈을 가져올 수 있습니다.

Module은 요청마다 거쳐 가는 처리 단계가 아니라, **애플리케이션의 구성과 의존 관계를 정의하는 단위**입니다.

## 3. Controller란?

Controller는 클라이언트의 요청을 받아 알맞은 메서드에서 처리하고 응답을 반환하는 역할을 합니다.

```ts
@Controller('boards')
export class BoardsController {
  @Get()
  findAll() {
    return '게시글 목록';
  }
}
```

`@Controller('boards')`는 공통 경로를 지정하고, `@Get()`은 GET 요청을 처리할 메서드를 지정합니다. 위 예제는 별도의 전역 경로 설정이 없다면 `GET /boards` 요청을 처리합니다.

Controller에서는 요청 본문이나 경로 파라미터 등을 가져올 수도 있습니다.

| 데코레이터 | 역할                              |
| ---------- | --------------------------------- |
| `@Body()`  | 요청 본문을 가져옵니다.           |
| `@Param()` | URL의 경로 파라미터를 가져옵니다. |
| `@Query()` | URL의 쿼리 파라미터를 가져옵니다. |

실제 애플리케이션에서는 Controller가 요청과 응답 처리에 집중하고, 조회·저장 같은 로직은 Service에 맡기도록 나눌 수 있습니다.

## 4. Provider와 Service는 어떤 관계일까?

Provider는 NestJS의 의존성 주입 시스템에서 관리하고 제공할 수 있도록 등록하는 대상입니다. Service뿐 아니라 데이터 접근 클래스나 외부 서비스 연동 클래스 등도 Provider로 사용할 수 있습니다.

Service는 그중 **애플리케이션의 실제 처리 로직을 담당하는 데 흔히 사용하는 클래스**입니다.

```ts
@Injectable()
export class BoardsService {
  findAll() {
    return ['첫 번째 게시글', '두 번째 게시글'];
  }
}
```

`@Injectable()`은 NestJS가 클래스의 의존성을 주입하는 데 사용할 메타데이터를 제공합니다.

여기서 중요한 점은 **`@Injectable()`을 붙이는 것과 Provider로 등록하는 것은 별개의 작업**이라는 것입니다. 일반적인 클래스 Provider는 모듈의 `providers`에 등록합니다.

```ts
providers: [BoardsService]
```

이렇게 등록한 Service를 Controller나 다른 Provider에서 주입받아 사용할 수 있습니다.

## 5. 의존성과 DI란?

어떤 클래스가 동작하기 위해 다른 객체를 필요로 한다면, 그 객체를 의존성이라고 합니다.

예를 들어 `BoardsController`가 게시글을 조회하기 위해 `BoardsService`를 사용한다면, Controller는 Service에 의존합니다.

직접 생성하는 방식은 다음과 같습니다.

```ts
private readonly boardsService = new BoardsService();
```

이 방식에서는 Controller가 Service의 생성까지 담당합니다.

DI는 **Dependency Injection**, 즉 의존성 주입의 약자입니다. 필요한 객체를 내부에서 직접 만드는 대신 외부에서 전달받는 방식입니다.

NestJS에서는 생성자를 통해 주입받는 방식을 흔히 사용합니다.

```ts
constructor(
  private readonly boardsService: BoardsService,
) {}
```

NestJS가 등록된 Provider를 찾아 생성하고, 필요한 곳에 전달합니다. 생성자에 적는 `BoardsService`는 이 예제에서 어떤 Provider를 받을지 식별하는 기준으로도 사용됩니다.

이렇게 하면 객체를 사용하는 코드와 객체를 구성하는 책임을 나눌 수 있습니다. 테스트할 때 실제 Service 대신 테스트용 구현을 제공하기에도 도움이 됩니다.

## 6. 함께 연결해서 이해하기

Service를 주입받은 Controller는 다음처럼 사용할 수 있습니다.

```ts
@Controller('boards')
export class BoardsController {
  constructor(
    private readonly boardsService: BoardsService,
  ) {}

  @Get()
  findAll() {
    return this.boardsService.findAll();
  }
}
```

먼저 Module에 Controller와 Service를 등록하면, NestJS는 그 정보를 바탕으로 필요한 의존성을 연결합니다. 위 예제에서는 `BoardsController`를 생성할 때 `BoardsService`를 주입합니다.

이후 `GET /boards` 요청이 들어오면 Controller의 `findAll()`이 실행되고, 주입받은 Service의 `findAll()`을 호출합니다. Service가 반환한 게시글 목록은 Controller를 통해 응답으로 전달됩니다.

Module은 구성을 정의하고, Controller는 요청을 처리하며, Service는 실제 로직을 수행합니다. DI는 이렇게 필요한 구성 요소를 연결하는 방식입니다.

## 7. 기억할 점

Provider로 등록했다고 모든 모듈에서 자동으로 사용할 수 있는 것은 아닙니다. 다른 모듈에서 사용하려면 일반적으로 제공하는 모듈의 `exports`와 사용하는 모듈의 `imports`를 통해 연결해야 합니다.

또한 DI와 싱글톤은 서로 다른 개념입니다. DI는 **의존성을 전달하는 방식**이고, 싱글톤은 **인스턴스를 생성하고 공유하는 방식**입니다. NestJS Provider는 기본적으로 싱글톤 범위를 사용하지만, 필요에 따라 다른 범위로 설정할 수도 있습니다.
