Next.js나 Vite로 프로젝트를 만들면 `pnpm dev` 한 줄로 개발 서버가 뜨고, `pnpm build` 한 줄로 배포 파일이 만들어집니다. 이 두 명령 뒤에서 일하는 도구가 **번들러**입니다.

번들러가 무엇을 하는지 알면 개발 서버가 느려질 때, 배포 파일이 지나치게 커질 때, `next.config`나 `vite.config` 같은 설정 파일을 열었을 때 어떤 부분을 봐야 하는지 판단할 수 있습니다. 이 글에서는 번들러가 필요한 이유와 하는 일을 먼저 살펴보고, 대표적인 번들러인 Webpack, Vite, Turbopack이 각각 어떤 방식으로 동작하는지 정리합니다.

## 번들러가 필요한 이유

우리가 작성하는 코드는 보통 여러 파일로 나뉘어 있고, npm으로 설치한 라이브러리를 가져다 씁니다.

```tsx
// src/App.tsx
import { useState } from 'react';
import { Header } from './components/Header';
import './styles.css';
```

이 코드를 브라우저에 그대로 보내면 몇 가지 문제가 생깁니다.

- **브라우저가 이해하지 못하는 코드가 있습니다.** TypeScript와 JSX는 브라우저가 바로 실행할 수 없습니다. 또 브라우저는 별도 설정 없이는 `'react'`가 `node_modules`의 어느 파일인지 알지 못합니다.
- **파일 수만큼 요청이 생깁니다.** 컴포넌트 파일과 라이브러리 내부 파일까지 합치면 수백 개가 넘는 경우가 흔합니다. 파일마다 따로 요청하면 페이지가 뜨기까지 오래 걸립니다.
- **쓰지 않는 코드까지 전달됩니다.** 라이브러리에서 함수 하나만 가져와도 라이브러리 전체가 내려갈 수 있습니다.

번들러는 이런 문제를 빌드 단계에서 해결해, 브라우저가 바로 실행할 수 있고 내려받기 좋은 형태로 파일을 만들어 줍니다.

## 번들러가 하는 일

번들러의 동작은 크게 네 단계로 나눌 수 있습니다.

1. **의존성 그래프 만들기**: 시작 파일(entry)에서 `import`를 따라가며 어떤 파일이 어떤 파일을 쓰는지 연결합니다.
2. **변환하기**: TypeScript·JSX를 JavaScript로 바꾸고, CSS나 이미지 같은 파일도 처리합니다.
3. **묶기**: 연결된 모듈을 몇 개의 파일(번들, 청크)로 합칩니다.
4. **최적화하기**: 배포용 결과물의 크기를 줄이고 캐시하기 좋게 만듭니다.

4단계 최적화에는 다음과 같은 기법이 쓰입니다.

| 기법          | 하는 일                                                                                      |
| ------------- | -------------------------------------------------------------------------------------------- |
| 코드 스플리팅 | 큰 번들을 여러 청크로 나눠, 지금 필요한 코드만 먼저 내려받게 합니다                          |
| 트리 셰이킹   | `import`/`export`를 분석해 실제로 쓰지 않는 코드를 제거합니다                                |
| 압축(minify)  | 공백·주석을 지우고 변수 이름을 짧게 바꿔 파일 크기를 줄입니다                                |
| 콘텐츠 해시   | 파일 이름에 내용 기반 해시(`main.a1b2c3.js`)를 붙여, 내용이 바뀐 파일만 새로 내려받게 합니다 |

코드 스플리팅은 동적 `import()`를 기준으로 동작하는 경우가 많습니다. React에서는 `lazy`와 함께 씁니다.

```tsx
import { lazy } from 'react';

// Chart 컴포넌트는 별도 청크로 분리되고, 처음 렌더링될 때 내려받습니다.
const Chart = lazy(() => import('./Chart'));
```

트리 셰이킹은 `import`/`export`처럼 빌드 시점에 구조가 정해지는 ES Module에서 잘 동작합니다. `require()`를 쓰는 CommonJS는 실행해 봐야 무엇을 가져오는지 알 수 있는 경우가 많아 효과가 제한됩니다.

이 개념들은 어떤 번들러를 쓰든 같습니다. 번들러마다 다른 점은 **개발 서버에서 코드를 어떻게 전달하는지**, 그리고 **어떤 도구로 변환과 빌드를 처리하는지**입니다.

## Webpack

Webpack은 2012년에 공개된 번들러로, 오랫동안 JavaScript 생태계의 표준처럼 쓰였습니다.

- JavaScript뿐 아니라 CSS, 이미지, 폰트까지 모든 파일을 **모듈**로 다룹니다.
- **loader**로 파일을 변환하고(예: TypeScript → JavaScript), **plugin**으로 빌드 과정 자체를 확장합니다. 이 구조 덕분에 거의 모든 동작을 직접 설정할 수 있습니다.
- 개발 서버는 기본적으로 애플리케이션 전체의 번들을 먼저 만든 뒤 브라우저에 제공합니다. 그래서 프로젝트가 커질수록 개발 서버 시작과 변경 반영이 느려지기 쉽습니다.

## Vite

Vite는 Vue를 만든 Evan You가 2020년에 공개한 빌드 도구입니다. 이름은 프랑스어로 "빠르다"는 뜻입니다.

Vite는 개발 서버에서 **번들을 미리 만들지 않습니다.** 대신 브라우저가 지원하는 네이티브 ES Module(`<script type="module">`)을 활용해, 브라우저가 요청한 파일만 그때그때 변환해서 보내 줍니다. 처음 접속한 페이지에 필요한 파일만 처리하면 되므로, 프로젝트가 커져도 개발 서버가 빠르게 뜹니다.

다만 `node_modules`의 라이브러리는 미리 묶어 둡니다. 이를 **의존성 프리번들링**이라고 합니다. 예를 들어 `lodash-es`는 내부 모듈이 수백 개라, 그대로 두면 브라우저가 수백 번 요청을 보내야 합니다. CommonJS로 배포된 라이브러리를 ES Module로 바꾸는 일도 이 단계에서 합니다.

Vite가 내부에서 쓰는 도구는 버전에 따라 다릅니다.

- **Vite 7까지**: 개발 중 프리번들링은 esbuild(Go), 프로덕션 빌드는 Rollup이 맡았습니다. 두 도구가 달라 개발과 배포 결과가 미묘하게 어긋나는 문제가 있었습니다.
- **Vite 8부터**: Rust로 작성된 **Rolldown** 하나가 프리번들링과 프로덕션 빌드를 모두 맡습니다. 코드 파싱·변환·압축은 **Oxc**가 처리합니다.

## Turbopack

Turbopack은 Vercel이 Rust로 만든 번들러로, Next.js에 내장되어 있습니다. Webpack을 만든 Tobias Koppers가 개발을 이끌었습니다.

- **개발 중에도 번들링하되, 요청된 부분만 처리합니다.** Vite처럼 파일을 하나씩 보내면 큰 앱에서 요청 수가 많아질 수 있어, Turbopack은 필요한 부분만 골라 묶는 방식을 택했습니다.
- **작업 결과를 함수 단위로 캐시합니다.** 한 번 계산한 결과는 다시 계산하지 않고, 디스크에 저장해 다음 실행에서도 재사용합니다. 파일 하나를 고치면 그 파일과 관련된 작업만 다시 합니다.
- **Next.js 16부터 기본 번들러입니다.** 15.0에서 개발 서버용으로 안정화됐고, 16.0에서 프로덕션 빌드까지 안정화되면서 기본값이 됐습니다.

Next.js 16에서는 별도 플래그 없이 Turbopack을 씁니다. Webpack이 필요하면 `--webpack`을 붙입니다.

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build"
  }
}
```

```bash
next dev --webpack
next build --webpack
```

### Next.js에서 Vite를 쓸 수 있을까?

쓸 수 없습니다. Next.js가 공식적으로 지원하는 번들러는 Turbopack과 Webpack뿐입니다. 파일 기반 라우팅, 서버 컴포넌트, 이미지·폰트 최적화 같은 Next.js 기능이 자체 빌드 과정과 맞물려 동작하기 때문에 번들러만 Vite로 바꿀 수 있는 구조가 아닙니다. Vite를 기반으로 하는 React 프레임워크로는 React Router(프레임워크 모드)나 TanStack Start가 있습니다.

## 한눈에 비교하기

| 구분          | Webpack                                           | Vite                                       | Turbopack                             |
| ------------- | ------------------------------------------------- | ------------------------------------------ | ------------------------------------- |
| 공개          | 2012년                                            | 2020년                                     | 2022년                                |
| 만든 곳       | Tobias Koppers, 오픈소스 커뮤니티                 | Evan You, 오픈소스 커뮤니티                | Vercel                                |
| 핵심 구현     | JavaScript                                        | Rolldown·Oxc(Rust)                         | Rust                                  |
| 개발 서버     | 전체 번들을 만든 뒤 제공                          | 요청한 파일만 변환해 네이티브 ESM으로 제공 | 요청한 부분만 번들링                  |
| 프로덕션 빌드 | Webpack                                           | Rolldown(Vite 8 기준)                      | Turbopack                             |
| 확장 방식     | loader, plugin                                    | Vite·Rolldown 플러그인                     | `turbopack` 설정, 일부 Webpack loader |
| 주로 쓰는 곳  | 기존 프로젝트, 세밀한 빌드 설정이 필요한 프로젝트 | React·Vue·Svelte 등 다양한 프로젝트        | Next.js                               |

## 알아 둘 점

- **속도 차이는 프로젝트마다 다릅니다.** 번들러 간 속도 비교는 프로젝트 규모와 구조에 따라 결과가 크게 달라지므로, 벤치마크 수치보다 동작 방식의 차이로 이해하는 편이 정확합니다.
- **Turbopack은 Webpack 설정을 그대로 쓰지 못합니다.** `next.config`의 `webpack()` 설정과 Webpack 플러그인은 지원하지 않고, 지원하지 않는 기능이 있다고 Webpack으로 자동 전환되지도 않습니다. 필요하면 `--webpack`으로 직접 바꿔야 합니다.
- **버전에 따라 내부 도구가 다릅니다.** Vite 7 이하를 기준으로 쓴 자료는 esbuild와 Rollup을, Next.js 15 이하를 기준으로 쓴 자료는 `--turbo` 같은 플래그를 설명합니다. 자료를 볼 때 기준 버전을 먼저 확인합니다.
