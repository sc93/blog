브라우저는 HTML을 받은 뒤 여러 단계를 거쳐 화면에 픽셀을 그립니다. 이 과정을 Critical Rendering Path라고 부릅니다. 웹 최적화 기법은 흔히 목록으로 외우지만, 하나하나 들여다보면 모두 이 파이프라인의 특정 단계를 겨냥하고 있습니다. 단계를 알면 첫 화면이 늦게 뜨거나, 클릭에 반응이 느리거나, 화면이 밀리는 문제를 보고 어느 단계를 의심해야 할지 판단할 수 있습니다.

이 글은 렌더링을 단계별로 나눠 각 단계에서 무슨 일이 일어나는지, 어디서 느려지는지, 어떻게 최적화할 수 있는지 정리합니다.

## 1. 브라우저가 화면을 그리는 과정

<Image
  src="/images/browser-rendering-pipeline/01-rendering-pipeline.svg"
  alt="HTML과 CSS가 각각 DOM과 CSSOM이 되고, Render Tree, Layout, Paint, Composite를 거쳐 화면이 되는 렌더링 파이프라인. 각 단계에 이 글의 섹션 번호가 표시되어 있다."
  width={1290}
  height={460}
/>

그림의 번호는 이 글의 섹션 번호입니다.

1. HTML을 파싱해 **DOM**을 만듭니다.
2. CSS를 파싱해 **CSSOM**을 만듭니다.
3. 파싱 중 스크립트를 만나면 **JavaScript**를 실행합니다. JS는 DOM과 CSSOM을 바꿀 수 있어서 파싱을 멈추게 할 수 있습니다.
4. DOM과 CSSOM을 합쳐 화면에 보일 요소만 담은 **Render Tree**를 만듭니다.
5. **Layout**에서 각 요소의 위치와 크기를 계산합니다.
6. **Paint**에서 텍스트, 색, 테두리, 그림자를 픽셀로 그립니다.
7. **Composite**에서 여러 레이어를 합쳐 최종 화면을 만듭니다.

<Callout type="note" title="실제 브라우저와의 차이">
  Chrome 내부에서는 Render Tree 대신 Layout Tree라는 이름을 쓰고, Paint와
  Composite 사이에 래스터화 같은 단계가 더 있습니다. 이 글은 개념 설명에서
  흔히 쓰는 단계로 나눕니다.
</Callout>

각 단계를 최적화하는 방법은 결국 세 가지로 묶입니다. 2장의 모든 방법을 이 기준으로 읽으면 됩니다.

- **① 빨리 시작하게 하기**: 필요한 리소스를 더 일찍 받습니다.
- **② 작업량 줄이기**: 각 단계가 처리할 양을 줄입니다.
- **③ 다시 실행하지 않게 하기**: 이미 끝난 단계를 반복하지 않습니다.

## 2. 단계별 동작 원리와 최적화 방법

### 2-1. HTML → DOM

브라우저는 받은 바이트를 문자로, 문자를 토큰으로, 토큰을 노드로 바꿔 DOM 트리를 만듭니다. HTML을 끝까지 받을 때까지 기다리지 않고 **받은 만큼 점진적으로 파싱**합니다. 그래서 HTML이 일찍 도착할수록 모든 단계가 일찍 시작됩니다.

파서가 스크립트 때문에 멈춰 있는 동안에도 **프리로드 스캐너**가 뒤쪽 HTML을 미리 훑어 `img`, `link`, `script`를 먼저 요청합니다. 다만 JS로 삽입하는 리소스나 CSS의 `background-image`처럼 HTML에 드러나지 않는 리소스는 찾지 못합니다.

**이 단계가 느려지는 이유**

- HTML 자체가 늦게 도착합니다.
- DOM이 너무 크고 깊습니다. DOM이 크면 이후 Style, Layout 단계의 비용도 함께 커집니다.
- 중요한 리소스가 프리로드 스캐너에 보이지 않아 늦게 요청됩니다.

**최적화 방법**

**① HTML을 빨리 보냅니다.** SSR이나 SSG로 완성된 HTML을 보내고, 스트리밍(Next.js의 `Suspense`)으로 준비된 부분부터 먼저 보냅니다. gzip이나 brotli로 압축하고 CDN에 캐시합니다.

렌더링 전략은 [렌더링 전략이 중요한 이유](/blog/rendering-strategies-concepts)에서 다뤘습니다.

**② DOM 크기를 줄입니다.** 불필요한 래퍼 `div`를 걷어내고, 수천 개 행이 있는 긴 목록은 화면에 보이는 행만 렌더링하는 가상화(react-window 등)를 씁니다.

**③ 중요한 리소스를 일찍 발견하게 합니다.** LCP 이미지처럼 중요한 리소스는 HTML에 직접 두거나 `preload`로 알려 주고, 외부 도메인은 `preconnect`로 연결을 미리 맺습니다.

```html
<head>
  <!-- 외부 도메인 연결(DNS, TCP, TLS)을 미리 맺는다 -->
  <link rel="preconnect" href="https://cdn.example.com" />
  <!-- CSS 배경 등 HTML에 드러나지 않는 LCP 이미지를 미리 요청한다 -->
  <link rel="preload" as="image" href="/hero.webp" fetchpriority="high" />
</head>
```

이미지 우선순위는 [브라우저는 어떤 이미지를 다운로드할까?](/blog/browser-image-optimization)에서 자세히 다뤘습니다.

### 2-2. CSSOM과 Render Tree

CSS는 파싱되어 CSSOM이 됩니다. HTML과 달리 CSS는 **전부 받아야 적용할 수 있습니다.** 뒤에 나오는 규칙이 앞의 규칙을 덮어쓰는 캐스케이드 때문에, 일부만 보고는 최종 스타일을 확정할 수 없기 때문입니다. 미완성 CSSOM으로 화면을 그리면 스타일 없는 화면이 잠깐 보이는 FOUC가 생깁니다. 그래서 브라우저는 CSSOM이 완성될 때까지 렌더링을 미룹니다. CSS가 **렌더링 차단 리소스**인 이유입니다.

CSS는 스크립트 실행도 막습니다. 스크립트가 `getComputedStyle`처럼 스타일을 읽을 수 있으므로, 앞에 있는 CSS가 다 로드될 때까지 그 뒤의 스크립트는 실행되지 않습니다.

DOM과 CSSOM이 준비되면 둘을 합쳐 Render Tree를 만듭니다. Render Tree에는 **화면에 보이는 요소만** 들어갑니다.

<Image
  src="/images/browser-rendering-pipeline/02-render-tree.svg"
  alt="DOM 트리와 CSSOM 트리가 합쳐져 Render Tree가 되는 그림. display: none이 적용된 div.ad는 Render Tree에서 제외된다."
  width={1390}
  height={520}
/>

`head`, `script`처럼 화면에 보이지 않는 요소와 `display: none` 요소는 Render Tree에서 빠집니다. 반면 `visibility: hidden` 요소는 보이지 않아도 자리를 차지하므로 포함됩니다.

**이 단계가 느려지는 이유**

- CSS 파일이 크거나, 첫 화면과 상관없는 CSS까지 모두 렌더링을 막습니다.
- `@import`가 연쇄되면 CSS 파일을 하나 받은 뒤에야 다음 파일을 요청합니다.
- 화면 밖 요소까지 렌더링 작업에 포함됩니다.

**최적화 방법**

**① 첫 화면에 필요한 CSS만 먼저 적용합니다.** 첫 화면(above the fold)에 필요한 Critical CSS는 `<style>`로 인라인하고 나머지는 나중에 불러옵니다. CSS Modules처럼 컴포넌트·라우트 단위로 CSS를 나누면 페이지마다 필요한 CSS만 받게 됩니다.

**② CSS 용량을 줄입니다.** 사용하지 않는 CSS를 제거하고 압축합니다. Tailwind CSS는 빌드 때 실제로 쓴 클래스만 만들어 이 문제를 줄입니다. `@import` 대신 `link` 태그를 쓰거나 번들러로 합칩니다.

**③ 당장 필요 없는 CSS는 렌더링을 막지 않게 합니다.** `media` 속성 조건에 맞지 않는 CSS는 다운로드는 되지만 렌더링을 막지 않습니다.

```html
<link rel="stylesheet" href="/print.css" media="print" />
<link rel="stylesheet" href="/desktop.css" media="(min-width: 1024px)" />
```

**④ 화면 밖 요소의 렌더링을 미룹니다.** `content-visibility: auto`를 주면 화면 밖에 있는 요소 내부의 Style, Layout, Paint 작업을 건너뜁니다. 스크롤 위치가 튀지 않도록 `contain-intrinsic-size`로 예상 크기를 함께 지정합니다.

### 2-3. JavaScript

파서는 일반 `<script>`를 만나면 HTML 파싱을 멈추고, 스크립트를 다운로드하고 실행한 뒤에 파싱을 이어갑니다. 스크립트가 `document.write`나 DOM 조작으로 문서를 바꿀 수 있기 때문입니다.

<Image
  src="/images/browser-rendering-pipeline/03-script-async-defer.svg"
  alt="일반 script, async, defer 스크립트의 HTML 파싱, 다운로드, 실행 시점을 비교한 타임라인. 일반 script는 다운로드와 실행 동안 파싱이 멈추고, async는 다운로드가 끝나는 즉시 실행되며, defer는 파싱이 끝난 뒤 실행된다."
  width={1280}
  height={470}
/>

**이 단계가 느려지는 이유**

- 파서를 막는 스크립트가 다운로드·실행되는 동안 DOM 생성이 멈춥니다.
- 번들이 크면 파싱, 컴파일, 실행이 메인 스레드를 오래 점유합니다. 메인 스레드는 렌더링과 사용자 입력 처리도 함께 맡기 때문에 그동안 화면이 멈춥니다.

**최적화 방법**

**① defer와 async로 파싱과 분리합니다.** 두 속성 모두 다운로드는 HTML 파싱과 병렬로 진행합니다. `async`는 다운로드가 끝나는 즉시 실행되어 그 순간 파싱을 멈추고, 실행 순서가 보장되지 않습니다. `defer`는 파싱이 끝난 뒤 문서에 적힌 순서대로 실행됩니다. 그래서 DOM에 의존하거나 실행 순서가 중요한 스크립트는 `defer`, 분석 도구처럼 다른 코드와 독립적인 스크립트는 `async`를 씁니다.

`type="module"` 스크립트는 기본적으로 `defer`처럼 동작합니다. Next.js에서는 `next/script`의 `strategy`(`beforeInteractive`, `afterInteractive`, `lazyOnload`)로 로드 시점을 정합니다.

**② 실행할 코드의 양을 줄입니다.** `import()`, `React.lazy`, `next/dynamic`으로 코드를 나눠 지금 필요한 코드만 받습니다. 모달, 차트, 에디터처럼 첫 화면에 없는 무거운 컴포넌트가 1순위 대상입니다.

**③ 긴 작업을 쪼갭니다.** 50ms를 넘는 작업은 Long Task로 분류되고, 그동안 클릭이나 입력에 반응하지 못해 INP가 나빠집니다. 큰 작업은 나눠서 중간중간 메인 스레드를 양보합니다. React에서는 `useTransition`으로 급하지 않은 업데이트의 우선순위를 낮출 수 있습니다.

```javascript
// 지원 브라우저에서는 scheduler.yield(), 아니면 setTimeout으로 양보한다
const yieldToMain = () =>
  globalThis.scheduler?.yield
    ? scheduler.yield()
    : new Promise((resolve) => setTimeout(resolve, 0));

async function processAll(items) {
  for (let i = 0; i < items.length; i++) {
    process(items[i]);
    // 100개마다 입력 처리와 렌더링 기회를 준다
    if ((i + 1) % 100 === 0) await yieldToMain();
  }
}
```

[web.dev: 긴 작업 최적화](https://web.dev/articles/optimize-long-tasks)

### 2-4. Layout

Layout은 Render Tree의 각 요소가 뷰포트의 어디에, 어떤 크기로 놓일지 계산하는 단계입니다. 한 요소의 크기가 바뀌면 형제, 자식, 부모 요소의 위치까지 다시 계산될 수 있습니다. 이렇게 Layout이 다시 실행되는 것을 **Reflow**라고 부릅니다.

**이 단계가 느려지는 이유**

- 이미지나 폰트가 늦게 로드되면서 크기가 바뀌어 Layout이 다시 실행되고, 화면이 밀립니다(CLS).
- JS에서 스타일을 바꾼 직후 레이아웃 값을 읽으면 브라우저가 Layout을 즉시 실행합니다. 이를 **강제 동기 레이아웃**이라고 하고, 반복문 안에서 일어나면 **레이아웃 스래싱**이 됩니다.

<Image
  src="/images/browser-rendering-pipeline/04-layout-thrashing.svg"
  alt="읽기와 쓰기를 번갈아 하면 Layout이 매번 강제로 실행되고, 읽기를 모은 뒤 쓰면 프레임당 한 번만 실행되는 것을 비교한 그림."
  width={1280}
  height={360}
/>

**최적화 방법**

**① 크기를 미리 정해 둡니다.** 이미지에는 `width`, `height`나 `aspect-ratio`를 지정해 로드 전부터 자리를 확보합니다. `next/image`는 정적 import나 `fill`을 쓰지 않으면 크기를 필수로 받아 이 문제를 막고, `next/font`는 대체 폰트의 크기를 웹 폰트에 맞춰 폰트가 바뀔 때 생기는 밀림을 줄입니다. 광고나 임베드 영역도 `min-height`로 자리를 예약합니다.

**② 레이아웃 값 읽기와 스타일 쓰기를 분리합니다.**

```javascript
// ❌ 반복마다 쓰기 → 읽기가 이어져 강제 동기 레이아웃이 매번 발생한다
boxes.forEach((box) => {
  box.style.width = `${box.offsetWidth + 10}px`;
});

// ✅ 읽기를 먼저 모은 뒤 한 번에 쓴다
const widths = boxes.map((box) => box.offsetWidth);
boxes.forEach((box, i) => {
  box.style.width = `${widths[i] + 10}px`;
});
```

`offsetWidth`, `offsetHeight`, `getBoundingClientRect()`, `scrollTop` 같은 값은 최신 레이아웃을 돌려줘야 해서 강제 동기 레이아웃을 일으킵니다. React의 `useLayoutEffect`에서 DOM을 측정하는 코드도 같은 원리로 동작하므로, 측정과 변경을 섞지 않습니다.

**③ Layout의 영향 범위를 제한합니다.** `contain: layout`을 지정하면 그 요소 내부의 변경이 바깥 요소의 Layout에 영향을 주지 않습니다. 위젯이나 카드처럼 독립적인 영역에 쓸 수 있습니다.

### 2-5. Paint와 Composite

Paint는 요소의 텍스트, 색, 테두리, 그림자를 픽셀로 그리는 단계이고, Composite는 따로 그린 여러 레이어를 순서대로 겹쳐 최종 화면을 만드는 단계입니다. 별도 레이어로 분리된 요소는 다른 부분을 다시 그리지 않고 위치나 투명도만 바꿔 합성할 수 있습니다.

어떤 CSS 속성을 바꾸느냐에 따라 파이프라인의 어느 단계부터 다시 실행될지가 달라집니다.

<Image
  src="/images/browser-rendering-pipeline/05-property-stages.svg"
  alt="width·top 같은 기하 속성은 Layout부터, color·box-shadow 같은 시각 속성은 Paint부터, transform·opacity는 Composite만 다시 실행되는 것을 비교한 그림."
  width={1400}
  height={450}
/>

**이 단계가 느려지는 이유**

- `top`, `width` 같은 속성으로 애니메이션을 만들면 매 프레임 Layout과 Paint가 다시 실행됩니다.
- 넓은 영역을 다시 그리거나, `box-shadow`, `filter: blur()`처럼 그리기 비용이 큰 속성을 자주 바꿉니다.
- 레이어가 지나치게 많아져 메모리를 낭비합니다.

**최적화 방법**

**① 애니메이션은 transform과 opacity로 만듭니다.** Layout과 Paint를 건너뛰고 Composite만 실행됩니다. 레이어로 분리된 요소의 `transform`, `opacity` 애니메이션은 메인 스레드가 아닌 컴포지터 스레드에서 처리될 수 있어, JS 실행으로 메인 스레드가 바빠도 부드럽게 움직입니다.

```css
/* ❌ 매 프레임 Layout → Paint → Composite */
.toast {
  transition: top 0.3s;
}
.toast.show {
  top: 20px;
}

/* ✅ Composite만 실행 */
.toast {
  transition: transform 0.3s;
}
.toast.show {
  transform: translateY(20px);
}
```

**② 비싼 속성은 직접 바꾸지 않습니다.** 호버 시 그림자를 키우고 싶다면 `box-shadow`를 직접 애니메이션하지 말고, 큰 그림자를 가진 가상 요소(`::after`)를 미리 만들어 두고 그 `opacity`만 바꿉니다.

**③ will-change는 필요한 곳에만 씁니다.** `will-change: transform`은 요소를 미리 별도 레이어로 올려 애니메이션 시작 시의 지연을 줄입니다. 하지만 레이어마다 메모리를 쓰기 때문에 모든 요소에 걸면 오히려 느려집니다. 실제로 애니메이션되는 요소에만, 가능하면 애니메이션 직전에 추가하고 끝나면 제거합니다.

## 핵심 요약

| 원칙                      | 최적화 방법                                                                                        |
| ------------------------- | -------------------------------------------------------------------------------------------------- |
| ① 빨리 시작하게 하기      | SSR·스트리밍, `preconnect`·`preload`·`fetchpriority`, `defer`·`async`                              |
| ② 작업량 줄이기           | DOM 크기 줄이기, Critical CSS·미사용 CSS 제거, 코드 스플리팅, 긴 작업 쪼개기, `content-visibility` |
| ③ 다시 실행하지 않게 하기 | 크기 미리 지정, 레이아웃 읽기·쓰기 분리, `contain`, `transform`·`opacity` 애니메이션               |

- CSS는 **렌더링**을, 일반 `<script>`는 **HTML 파싱**을 막습니다. 둘 다 빨리 받고, 적게 받고, 막지 않게 만드는 것이 핵심입니다.
- Layout은 DOM과 스타일이 바뀔 때마다 다시 실행될 수 있습니다. 크기를 예약하고 읽기와 쓰기를 분리해 재실행을 줄입니다.
- 바꾸는 속성에 따라 다시 실행되는 단계가 달라집니다. 움직임은 `transform`과 `opacity`로 만들어 앞 단계를 건너뜁니다.

## 마치며

렌더링 과정을 단계로 나눠 보면 최적화 기법이 따로 노는 팁이 아니라는 것이 보입니다. 새로운 기법을 만났을 때 "이 기법은 어느 단계를, 세 가지 원칙 중 무엇으로 줄이는가?"를 물으면, 왜 효과가 있는지와 언제 써야 하는지를 함께 설명할 수 있습니다.

다만 이 글의 단계 구분은 이해를 위한 모델이고, 실제 브라우저는 여러 작업을 겹치거나 엔진마다 다르게 처리합니다. `will-change`나 `content-visibility`처럼 잘못 쓰면 오히려 비용이 늘어나는 기법도 있습니다. 적용 전후로 개발자 도구의 Performance 패널에서 어느 단계가 실제로 오래 걸리는지 먼저 확인하는 것이 좋습니다.
