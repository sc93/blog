렌더링 전략을 잘못 고르면 기능은 동작해도 다른 곳이 깨집니다. 링크를 공유하면 모든 페이지의 미리보기 제목이 똑같이 나오고, 프로모션 트래픽이 몰리면 서버가 버티지 못하고, 수정한 내용이 한참 동안 반영되지 않습니다. 세 문제 모두 원인은 **HTML을 누가, 언제 만드느냐**에 있습니다.

이 글에서는 프레임워크와 무관하게 CSR, SSR, SSG, ISR을 정리합니다. Next.js에서의 구현은 다음 편에서 다룹니다.

## 1. 렌더링 전략 구분

| 전략 | 누가 HTML을 만드나 | 언제 만드나                           |
| ---- | ------------------ | ------------------------------------- |
| CSR  | 브라우저(JS)       | 접속한 뒤 런타임에                    |
| SSR  | 서버               | 요청마다                              |
| SSG  | 서버               | 빌드할 때 한 번                       |
| ISR  | 서버               | 빌드할 때 + 주기나 이벤트에 따라 다시 |

SSR, SSG, ISR은 모두 브라우저에 보내기 전에 서버에서 HTML을 만드는 **pre-rendering**입니다. 셋의 차이는 '언제'뿐입니다.

## 2. CSR

서버는 빈 HTML과 JS 번들만 전달하고, 브라우저가 JS를 실행해 화면을 만듭니다.

```txt
빈 HTML → JS 다운로드·실행 → 렌더링 → useEffect에서 fetch → 데이터 렌더링
```

모든 단계가 앞 단계를 기다리는 **워터폴**입니다. 중첩 컴포넌트가 각자 fetch하면 더 길어집니다.

- **첫 화면이 느립니다.** 번들이 실행될 때까지 흰 화면이나 스피너를 봅니다.
- **링크 미리보기가 깨집니다.** 메신저·SNS의 OG 크롤러는 대부분 JS를 실행하지 않고 초기 HTML만 읽습니다. 클라이언트에서 넣은 `og:title`은 무시되고 `index.html`의 공통 태그만 보입니다. Googlebot은 JS를 실행하지만 렌더링 큐를 거치므로 반영이 늦을 수 있습니다.
- **대신 서버가 가볍습니다.** 정적 파일만 서빙하면 되고, 첫 로드 이후 전환이 빠릅니다.

개선은 코드 스플리팅, 라우트 진입 시점의 병렬 prefetch, 스켈레톤 UI로 합니다. SEO가 필요 없는 어드민·대시보드라면 CSR이 합리적인 선택입니다.

[Google 검색 센터: JavaScript SEO 기본사항](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

## 3. SSR

서버가 요청마다 데이터를 조회해 HTML을 만듭니다. SEO와 개인화(쿠키, 인증, 지역)가 모두 가능하고, 클라이언트 워터폴이 사라집니다.

대신 대가가 있습니다.

- **첫 응답이 느려집니다.** 첫 바이트까지 걸리는 시간(TTFB)이 서버 작업 시간만큼 늘어납니다.
- **트래픽이 곧 연산량입니다.** 캐시가 없다면 트래픽이 100배가 될 때 렌더링과 DB 조회도 100배가 됩니다.
- **CDN 캐시가 제한됩니다.** 사용자별 응답은 CDN에 캐시할 수 없습니다.

## 4. SSG

렌더링을 빌드 시점으로 옮깁니다. 요청 시점에는 CDN이 파일만 주므로 TTFB가 가장 빠르고, 트래픽이 몰려도 연산이 늘지 않으며, 장애 지점도 적습니다.

한계는 세 가지입니다.

- **데이터가 빌드 시점에 고정됩니다.** 수정하려면 다시 빌드해야 합니다.
- **빌드 시간이 페이지 수에 비례합니다.** 상품 10만 개를 100ms씩 순차로 만들면 약 2.8시간입니다. 빌드 후 추가된 경로는 404가 납니다.
- **요청별 정보를 쓸 수 없습니다.** 빌드 시점에는 쿠키도, 로그인 사용자도 없습니다.

로그인 상태나 장바구니처럼 사용자별 영역은 SSG 페이지 위에서 클라이언트 fetch로 채웁니다. 공통이고 SEO가 필요한 부분은 정적으로, 사용자별·실시간 부분은 동적으로 두는 혼합이 기본입니다.

## 5. ISR

ISR이라는 이름은 Next.js가 만들었지만, 원리는 HTTP 캐싱의 **stale-while-revalidate**입니다. 캐시된 응답을 먼저 주고 백그라운드에서 갱신합니다. 이를 미리 렌더링한 페이지에 적용하면 페이지 단위로 다시 만들고(점진적 재생성), 빌드하지 않은 페이지는 첫 요청 때 만들어 캐시합니다(점진적 생성). 앞서 본 SSG의 데이터 고정과 빌드 시간 문제를 각각 해결합니다. 빌드하지 않은 경로의 첫 요청은 완성될 때까지 기다리는 블로킹 방식이 SEO에 안전합니다.

[RFC 5861: HTTP Cache-Control Extensions for Stale Content](https://datatracker.ietf.org/doc/html/rfc5861)

### 재검증 동작

재검증 주기가 60초라고 가정합니다.

```txt
t=0s    빌드 → v1 캐시
t=59s   DB에서 가격 수정
t=70s   방문자 B → v1 (stale) + 백그라운드 재생성 트리거
t=72s   재생성 완료 → v2로 교체
t=75s   방문자 C → v2
```

- **주기가 지난 뒤 첫 방문자는 옛 페이지를 받습니다.** 기다리지 않는 대신 신선도를 양보합니다.
- **cron이 아닙니다.** 주기가 지난 뒤 요청이 와야 재생성됩니다. 트래픽이 없으면 하루가 지나도 v1입니다.
- **재생성에 실패하면 마지막 성공 버전을 계속 줍니다.** SSR이라면 사용자가 에러를 봤을 상황입니다.

변경 시점을 아는 데이터(CMS 발행 등)는 웹훅으로 경로나 태그를 무효화하는 **on-demand 재검증**을 쓰고, 시간 기반 주기는 웹훅 누락에 대비한 안전망으로 둡니다.

### SSR + CDN 캐시와의 차이

SSR 응답에 `Cache-Control: s-maxage=60, stale-while-revalidate=300`을 붙이고 CDN을 두면 원리는 거의 같습니다. 차이는 통합에 있습니다. ISR은 빌드 때 미리 생성하고, 프레임워크가 관리하는 영속 캐시를 쓰며, 경로·태그 단위로 무효화하고, 실패 시 마지막 성공 버전을 유지합니다. CDN 캐시는 트래픽이 적으면 밀려날 수 있고, 태그 무효화나 오류 시 stale 응답은 CDN의 기능과 설정에 따라 달라집니다.

### 한계

- 모든 사용자가 같은 캐시를 공유하므로 사용자별 데이터를 넣으면 다른 사람의 데이터가 보이는 사고가 납니다.
- 결제 금액이나 재고 0 판정처럼 stale이 허용되지 않는 값에는 맞지 않습니다. 최종 검증은 항상 서버에서 합니다.
- 직접 운영하는 서버가 여러 대면 각자 로컬 캐시를 가져 버전이 어긋날 수 있으므로 공유 캐시 저장소가 필요합니다.

[Next.js 공식 문서: ISR](https://nextjs.org/docs/app/guides/incremental-static-regeneration)

## 6. 전략 비교와 선택

|           | CSR       | SSR       | SSG               | ISR               |
| --------- | --------- | --------- | ----------------- | ----------------- |
| 첫 화면   | 느림      | 빠름      | 가장 빠름         | 가장 빠름         |
| SEO / OG  | 불리      | 좋음      | 좋음              | 좋음              |
| 신선도    | 요청 시점 | 요청 시점 | 빌드 시점         | 주기·이벤트       |
| 개인화    | 가능      | 가능      | 클라이언트 영역만 | 클라이언트 영역만 |
| 서버 비용 | 낮음      | 높음      | 거의 없음         | 낮음              |

판단 순서는 단순합니다. SEO와 링크 미리보기가 필요 없으면 CSR, HTML이 요청마다 달라야 하면 SSR, 모두에게 같고 거의 바뀌지 않으면 SSG, 자주 바뀌거나 페이지가 많으면 ISR입니다. 그리고 stale이 허용되지 않는 값만 따로 떼어 실시간으로 처리합니다.

쇼핑몰이라면 이렇게 섞습니다.

| 페이지                | 전략                           |
| --------------------- | ------------------------------ |
| 이용약관, 이벤트 랜딩 | SSG                            |
| 상품 상세             | ISR + on-demand, 재고는 실시간 |
| 검색 결과             | SSR                            |
| 장바구니, 마이페이지  | CSR 또는 캐시 없는 SSR         |

품절 상품이 구매 가능으로 보인다면 재검증 주기를 줄이기보다 재고만 분리하는 것이 맞습니다. 주기를 1초로 줄여도 첫 방문자는 stale을 받고 재생성 비용만 늘어납니다.

## 핵심 요약

- 전략은 HTML을 누가, 언제 만드느냐로 구분합니다. SSR·SSG·ISR의 차이는 시점입니다.
- CSR은 서버가 가볍지만 첫 화면과 링크 미리보기가 약하고, SSR은 최신·개인화가 가능하지만 서버 비용이 듭니다. SSG는 가장 빠르지만 빌드 시점에 고정되고, ISR은 빠르게 응답하면서 갱신하지만 주기가 지난 뒤 첫 방문자는 stale을 받습니다.
- 전략은 서비스 단위가 아니라 페이지, 나아가 영역 단위로 고릅니다.
