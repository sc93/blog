같은 이미지라도 처음 요청할 때와 반복해서 요청할 때의 응답 시간이 다를 수 있습니다. 서버의 변환과 캐시 재사용을 이해하면 전송량뿐 아니라 첫 응답의 비용을 판단하고, 원본을 교체했는데 이전 이미지가 남는 문제도 추적할 수 있습니다.

[1편](/blog/browser-image-optimization)에서는 브라우저의 파일 선택을, [2편](/blog/nextjs-image-optimization)에서는 `Image`가 만드는 후보를 살펴봤습니다. 이번에는 **Next.js 16.2.6의 기본 이미지 최적화 서버**가 그 요청을 어떻게 처리하는지 정리합니다.

## 1. 서버는 요청한 변형을 만들거나 재사용합니다

```txt
/_next/image?url=%2Fimages%2Flandscape.jpg&w=1200&q=75
```

서버는 원본 주소(`url`), 요청 너비(`w`), 품질(`q`) 등 요청 조건을 검증합니다. 재사용할 수 있는 결과가 없으면 원본을 가져와 크기를 조정하고 인코딩합니다. 같은 조건의 신선한 결과가 캐시에 있으면 변환 작업을 반복하지 않고 반환할 수 있습니다.

```txt
최적화 URL 요청 → 캐시 확인
  ├ 재사용 가능 → 결과 반환
  └ 결과 없음 → 원본 가져오기 → 크기 조정·인코딩 → 캐시 저장·반환
```

기본 최적화 서버는 요청 시점에 결과를 생성합니다. 정적 import에서 빌드 시 이미지 치수를 알아내는 작업과, 모든 크기의 변환 파일을 미리 생성하는 작업은 다릅니다. 위 흐름은 단순화한 것이며, 만료된 캐시의 재검증과 애니메이션 등에는 별도 처리가 있습니다.

[Next.js 공식 셀프 호스팅 가이드: 이미지 최적화](https://nextjs.org/docs/app/guides/self-hosting#image-optimization)

## 2. 크기·품질·포맷은 별도로 조절합니다

| 조절 대상 | 바꾸는 것                   | 확인할 질문                                |
| --------- | --------------------------- | ------------------------------------------ |
| 크기      | 이미지의 픽셀 수            | 표시 너비와 DPR에 필요한 해상도인가?       |
| 품질      | 압축 과정에서 보존하는 정보 | 눈에 띄는 손상 없이 용량을 줄일 수 있는가? |
| 포맷      | 이미지를 저장·압축하는 방식 | 이 이미지에 효율적인 형식인가?             |

너비 3000픽셀 사진을 CSS 너비 600px, DPR 2 환경에서 표시한다면 약 1200픽셀을 선택 기준으로 생각할 수 있습니다. 불필요하게 큰 파일을 받고 있다면 품질만 낮추기 전에 픽셀 크기부터 확인합니다. 반대로 원본 해상도가 부족하면 품질 값을 높여도 없던 디테일이 복원되지는 않습니다.

WebP는 손실·무손실 압축과 투명도를 지원합니다. AVIF는 AV1을 기반으로 하며 높은 압축 효율을 기대할 수 있습니다. 두 포맷 모두 전송량을 줄일 수 있지만, 이미지 특성과 인코더 설정에 따라 결과가 달라집니다. 같은 크기의 원본으로 시각적 품질과 파일 용량을 함께 비교해야 합니다.

[Google의 WebP 소개](https://developers.google.com/speed/webp)

[web.dev의 AVIF 설명](https://web.dev/learn/images/avif)

## 3. Accept와 서버 설정으로 출력 포맷을 선택합니다

브라우저가 보낸 `Accept` 헤더와 `images.formats` 설정을 비교해 출력 포맷을 정합니다. Next.js 16.2.6의 기본 설정은 WebP이며, 아래는 AVIF도 사용하면서 품질 60과 75를 허용하는 예제입니다.

```ts
// next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  images: {
    formats: ['image/avif', 'image/webp'],
    qualities: [60, 75],
    minimumCacheTTL: 14400,
  },
};

export default nextConfig;
```

둘 다 지원하는 동일한 우선도의 요청에서는 배열 앞의 AVIF가 우선됩니다. 일치하는 지원 포맷이 없으면 이 글의 JPEG 원본은 JPEG로 처리됩니다. 16.2.6 구현에서는 원본이 WebP·AVIF인 경우 JPEG로 처리하는 fallback도 있으므로, 항상 원본 포맷을 유지한다고 볼 수는 없습니다. 애니메이션 이미지는 원본을 그대로 전달하는 예외가 있습니다.

`qualities`는 허용할 품질 목록이며 기본값은 `[75]`입니다. `Image`의 `quality={60}`을 사용하려면 위처럼 허용 목록에도 포함합니다. 목록에 없는 컴포넌트 품질 값은 가까운 허용 값으로 보정되지만, 최적화 URL을 직접 요청할 때 허용되지 않는 `q`는 400 응답을 받습니다.

품질 숫자는 포맷 간 공통 화질 척도가 아닙니다. 같은 `quality={75}`라도 WebP와 AVIF의 시각적 품질이나 파일 용량이 같다는 뜻은 아닙니다.

[공식 Image API: formats와 qualities](https://nextjs.org/docs/app/api-reference/components/image#formats)

[Next.js 16.2.6의 출력 포맷 선택 구현](https://github.com/vercel/next.js/blob/v16.2.6/packages/next/src/server/image-optimizer.ts#L1090)

## 4. 같은 원본도 캐시 결과는 여러 개입니다

기본 구현의 캐시 키에는 원본 주소, 너비, 품질, 출력 MIME 타입과 내부 캐시 버전이 반영됩니다.

| 원본          | 요청 너비 | 품질 | 출력 포맷 |
| ------------- | --------- | ---- | --------- |
| landscape.jpg | 640       | 75   | WebP      |
| landscape.jpg | 1200      | 75   | WebP      |
| landscape.jpg | 1200      | 60   | WebP      |
| landscape.jpg | 1200      | 75   | AVIF      |

위 결과는 서로 다른 캐시 항목이 될 수 있습니다. WebP 결과가 있어도 AVIF 결과는 새로 만들어야 할 수 있고, 같은 사용자도 다른 너비를 요청하면 캐시에 없는 변형을 기다릴 수 있습니다. **첫 방문인지보다 요청한 변형이 캐시에 있는지가 중요합니다.**

너비·품질·포맷의 조합을 늘리면 가능한 결과 수도 많아집니다. 모든 조합을 빌드할 때 만들지는 않지만, 실제 요청되는 변형이 다양하면 변환 작업과 저장 공간도 늘어날 수 있습니다.

[Next.js 16.2.6의 이미지 캐시 키 구현](https://github.com/vercel/next.js/blob/v16.2.6/packages/next/src/server/image-optimizer.ts#L515)

## 5. 캐시 계층과 원본 교체를 함께 생각합니다

```txt
브라우저 캐시 → CDN·프록시 캐시 → 최적화 서버의 결과 캐시 → 원본 저장소
```

브라우저가 신선한 응답을 재사용하면 네트워크 요청을 생략할 수 있습니다. CDN에 결과가 있으면 최적화 서버까지 요청이 가지 않을 수 있고, 서버 캐시만 적중해도 재인코딩 비용을 줄일 수 있습니다. 브라우저 개발자 도구의 캐시 비활성화가 CDN과 서버 캐시까지 비우는 것은 아닙니다.

같은 URL에서도 `Accept`에 따라 응답 포맷이 달라질 수 있어 기본 최적화 응답은 `Vary: Accept`를 사용합니다. 프록시를 둔다면 해당 헤더를 서버로 전달하고, 캐시에서도 응답 변형을 구분해야 합니다.

[MDN의 HTTP 캐싱 설명](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

[Next.js 16.2.6의 응답 헤더 구현](https://github.com/vercel/next.js/blob/v16.2.6/packages/next/src/server/image-optimizer.ts#L1174)

`minimumCacheTTL`은 최적화 결과의 최소 캐시 유효 시간을 초 단위로 설정합니다. 기본값은 14400초, 즉 4시간입니다. 일반적인 최적화 결과의 유효 시간은 이 값과 원본 `Cache-Control`에서 읽은 시간 중 큰 값을 기준으로 합니다. 예를 들어 최소 TTL이 4시간이고 원본의 `max-age`가 24시간이면 기준은 24시간입니다. 원본에 `s-maxage`도 있으면 기본 구현은 이를 `max-age`보다 우선해 읽습니다.

기본 이미지 캐시에 범용 무효화 API는 없으므로 같은 URL의 내용만 덮어쓰면 이전 결과가 남을 수 있습니다. 파일명에 버전을 넣거나 정적 import의 콘텐츠 해시처럼 **내용 변경을 URL에 반영하는 방식**을 고려합니다.

```txt
/images/banner-v1.jpg → /images/banner-v2.jpg
```

[공식 Image API: minimumCacheTTL](https://nextjs.org/docs/app/api-reference/components/image#minimumcachettl)

## 6. 첫 변환과 캐시 재사용을 나눠 확인합니다

프로덕션 서버에서 같은 원본·너비·품질·`Accept` 조건으로 요청을 반복합니다. Network에서 `Content-Type`, 전송량, 응답 대기 시간과 다운로드 시간을 비교하고, 어느 캐시 계층의 응답인지 구분합니다.

다음 명령은 앞의 설정을 적용한 로컬 프로덕션 서버와 `public/images/landscape.jpg`가 있다고 가정합니다. 포트는 이 블로그의 기본값인 8888입니다.

```bash
curl -sS -D - -o /dev/null \
  -H 'Accept: image/avif,image/webp' \
  -w '\nTTFB=%{time_starttransfer}s total=%{time_total}s bytes=%{size_download}\n' \
  'http://localhost:8888/_next/image?url=%2Fimages%2Flandscape.jpg&w=1200&q=75'
```

`Accept`를 `image/webp`로 바꾸면 WebP 응답과 비교할 수 있습니다. `x-nextjs-cache`의 `MISS`·`HIT`·`STALE`이나 호스팅 전용 헤더는 참고하되, 하나의 헤더로 모든 계층의 캐시 상태를 판단하지 않습니다. 명령을 처음 실행했다고 서버에서도 최초 변환이라는 뜻은 아닙니다.

## 핵심 요약

- 서버는 요청한 크기·품질·포맷의 이미지를 생성하거나 캐시에서 재사용합니다.
- 같은 원본도 요청 조건에 따라 캐시가 달라지며, 브라우저·CDN·서버 캐시는 구분해야 합니다.
- 캐시 TTL과 원본 교체 전략을 함께 정하고, 변환 비용과 전송량을 실제 응답으로 확인합니다.

더 작은 포맷이 항상 더 빠른 화면 표시를 보장하지는 않습니다. 인코딩·디코딩 비용과 캐시 적중 여부도 영향을 줍니다. TTL이 지났다고 모든 사용자가 즉시 새 이미지를 받는 것도 아닙니다. 만료 후 재검증과 다른 캐시 계층의 정책을 함께 봐야 합니다. `curl`의 TTFB 역시 순수 인코딩 시간이나 브라우저의 표시 시점은 아니므로, 최종적으로는 시각적 품질과 LCP를 함께 측정합니다.

커스텀 로더와 외부 이미지 서비스를 사용하면 변환과 캐시의 담당 위치가 달라집니다. 정적 export에는 기본 최적화 서버가 없으므로 외부 서비스나 사전 변환 등을 고려합니다.

## 시리즈를 마치며

브라우저의 파일 선택, 컴포넌트의 후보 생성, 서버의 변환·재사용을 구분하면 흐릿한 이미지, 과도한 전송량, 느린 응답, 교체 후 남은 캐시를 어느 단계에서 조사할지 판단할 수 있습니다.
