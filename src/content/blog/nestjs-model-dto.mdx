오늘은 NestJS에서 데이터의 형태를 정의하는 Model과 DTO를 공부했습니다. 게시글 데이터를 표현하는 방법과, 요청으로 전달받을 데이터의 구조를 구분하는 방법을 배웠습니다.

비슷한 필드를 정의하는데 왜 따로 사용하는지, 각각 어떤 역할을 하는지 복습하며 정리해 보겠습니다.

## 1. 데이터의 구조를 정의하는 이유

게시글에는 제목과 내용이 있고, 서버에서 관리하는 게시글에는 식별자인 ID도 필요할 수 있습니다.

이런 구조를 코드로 정의하면 어떤 항목이 필요한지, 각 항목에 어떤 타입의 값이 들어가는지 명확하게 표현할 수 있습니다.

| 항목          | 타입     | 의미          |
| ------------- | -------- | ------------- |
| `id`          | `number` | 게시글 식별자 |
| `title`       | `string` | 게시글 제목   |
| `description` | `string` | 게시글 내용   |

TypeScript에서는 인터페이스나 클래스로 이러한 구조를 표현할 수 있습니다.

## 2. Model이란?

Model은 애플리케이션에서 다루는 데이터와 그 구조를 표현하는 개념입니다. 문맥에 따라 동작이나 규칙까지 포함할 수 있지만, 이번 학습에서는 게시글 데이터의 형태를 정의하는 의미로 사용합니다.

```ts
export interface Board {
  id: number;
  title: string;
  description: string;
}
```

`Board`는 게시글이 어떤 속성을 갖는지 나타냅니다. 이 타입을 사용하면 코드에서 게시글 데이터를 다룰 때 필요한 속성과 타입을 검사할 수 있습니다.

```ts
const board: Board = {
  id: 1,
  title: 'NestJS 공부',
  description: 'Model과 DTO 개념 정리',
};
```

다만 **Model이 반드시 인터페이스여야 하는 것은 아닙니다.** 프로젝트와 사용하는 도구에 따라 클래스 등으로 표현할 수도 있습니다. NestJS가 `Model`이라는 이름의 특정 구현 방식을 강제하지는 않습니다.

## 3. DTO란?

DTO는 **Data Transfer Object**의 약자로, 데이터를 전달할 때 사용하는 객체입니다. 요청이나 응답 등에서 어떤 형태의 데이터를 주고받을지 표현합니다.

게시글을 생성하는 요청에는 제목과 내용이 필요하지만, 서버에서 생성하는 ID까지 클라이언트가 전달할 필요는 없습니다.

```ts
export class CreateBoardDto {
  title!: string;
  description!: string;
}
```

`CreateBoardDto`는 게시글 생성 요청에서 사용할 데이터 구조를 나타냅니다.

속성의 `!`는 TypeScript에 초기화를 나중에 처리한다고 알리는 표기입니다. 필수값을 검사하거나 값을 자동으로 채우는 기능은 없습니다.

DTO는 생성 요청뿐 아니라 수정 요청이나 응답 등에도 사용할 수 있습니다. 전달 목적에 따라 필요한 항목이 달라지기 때문입니다.

## 4. Model과 DTO는 왜 구분할까?

애플리케이션에서 관리하는 데이터와 외부에서 전달받을 데이터는 같지 않을 수 있습니다.

| 구분               | 게시글 Model                      | 게시글 생성 DTO                     |
| ------------------ | --------------------------------- | ----------------------------------- |
| 목적               | 애플리케이션에서 다룰 게시글 표현 | 생성 요청으로 전달받을 데이터 표현  |
| 예시 필드          | `id`, `title`, `description`      | `title`, `description`              |
| 구조를 정하는 기준 | 게시글에 어떤 데이터가 필요한가?  | 생성 요청에 어떤 데이터가 필요한가? |

두 구조를 구분하면 요청에서 필요한 항목을 명확히 표현할 수 있습니다. 내부 데이터 구조가 바뀌더라도 요청 형식을 별도로 유지하기에도 도움이 됩니다.

```text
생성 요청                     서버에서 관리하는 게시글
title                         id
description                   title
                              description

CreateBoardDto                Board
```

DTO와 Model은 모양이 비슷할 수 있지만, **어떤 목적으로 사용하는 데이터인지**에 차이가 있습니다.

## 5. DTO를 클래스로 작성하는 이유

TypeScript의 인터페이스는 컴파일 과정에서 제거됩니다. 반면 클래스는 컴파일된 JavaScript에도 남습니다.

| 구분                             | 인터페이스 | 클래스 |
| -------------------------------- | ---------- | ------ |
| TypeScript 타입 표현             | 가능       | 가능   |
| 실행 시점에 존재                 | 제거됨     | 존재함 |
| 클래스 기반 검증 데코레이터 사용 | 불가       | 가능   |

NestJS 공식 문서에서는 DTO에 클래스를 사용하는 방식을 권장합니다. Pipe 같은 기능이 실행 시점에 클래스 정보를 활용할 수 있기 때문입니다.

예를 들어 이후 `class-validator`로 검증 규칙을 선언할 때도 DTO 클래스를 활용할 수 있습니다.

## 6. 요청 데이터와 DTO는 어떻게 연결될까?

클라이언트가 다음과 같은 JSON을 보냈다고 생각해 보겠습니다.

```json
{
  "title": "NestJS 공부",
  "description": "Model과 DTO 개념 정리"
}
```

Controller에서는 `@Body()`로 요청 본문을 가져오고, DTO 타입으로 기대하는 구조를 표현할 수 있습니다.

```ts
@Post()
create(@Body() dto: CreateBoardDto) {
  return dto;
}
```

여기서 `@Body()`는 요청 본문을 가져오는 역할을 하고, `CreateBoardDto`는 코드에서 사용할 데이터의 형태를 나타냅니다.

## 7. 기억할 점

DTO 클래스를 작성하고 타입을 지정했다고 해서 실제 요청값이 자동으로 검증되지는 않습니다. DTO에 없는 속성이 자동으로 제거되는 것도 아닙니다.

또한 요청 본문이 DTO 클래스의 인스턴스로 자동 변환된다고 가정해서는 안 됩니다. 검증과 변환에는 `ValidationPipe` 등의 별도 설정이 필요합니다.

Model과 DTO를 나누는 것은 데이터의 목적과 구조를 명확하게 표현하는 방법이며, 실제 입력값을 검사하는 작업은 별도로 다뤄야 합니다.
