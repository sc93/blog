이미지 최적화에서는 파일 크기뿐 아니라 브라우저가 이미지를 발견하는 시점, 화면에 필요한 해상도, 요청 우선순위, 레이아웃 안정성을 함께 고려해야 합니다.

이번 시리즈에서는 브라우저의 이미지 처리 원리부터 Next.js의 Image 컴포넌트, 서버의 이미지 변환과 캐시까지 살펴봅니다. 첫 편에서는 브라우저가 이미지 파일을 선택하고 화면에 표시하는 과정을 정리합니다.

## 1. 이미지가 화면에 나타나기까지

이미지는 대략 다음 흐름으로 화면에 나타납니다.

<b>HTML에서 이미지 발견 → 후보 선택 및 요청 → 다운로드 → 디코딩 → 화면에 그리기</b>

브라우저는 HTML을 읽으며 <code>img</code>의 이미지 주소를 발견합니다. 미리 리소스를 찾는 프리로드 스캐너도 이 과정에 참여할 수 있습니다. 그래서 처음 받은 HTML에 이미지 주소가 있으면 일찍 발견할 수 있습니다. JavaScript가 실행된 다음에야 이미지 요소나 주소를 만드는 구조라면 발견 시점이 늦어질 수 있습니다.

[Chrome의 LCP 리소스 발견 가이드](https://developer.chrome.google.cn/docs/performance/insights/lcp-discovery?hl=en)

선택한 이미지의 압축 데이터를 내려받았다고 바로 화면에 그릴 수 있는 것은 아닙니다. JPEG 같은 압축 데이터를 화면에 사용할 픽셀 데이터로 해석하는 <b>디코딩</b>이 필요합니다. 이후 레이아웃, 페인트, 합성 등의 렌더링 작업을 거쳐 이미지가 보입니다.

이 흐름은 이해를 위한 구분입니다. 실제 브라우저에서는 다운로드 중 점진적으로 이미지를 표시하거나 여러 작업을 겹쳐 처리할 수 있습니다. 레이아웃도 반드시 다운로드 이후에만 일어나는 것은 아닙니다.

따라서 “이미지가 늦게 보인다”는 현상에는 여러 원인이 있습니다. 주소를 늦게 발견했을 수도 있고, 다운로드가 오래 걸렸을 수도 있고, 다운로드 후 화면에 그리기까지 지연이 생겼을 수도 있습니다.

[web.dev의 LCP 단계별 분석](https://web.dev/articles/optimize-lcp)

## 2. 이미지 파일의 픽셀과 CSS 표시 크기

가로 1200픽셀, 세로 800픽셀인 사진을 예로 들어 보겠습니다. 파일에는 1200 × 800개의 픽셀이 있지만, 화면에서는 가로 400 CSS px로 표시할 수 있습니다.

이 글에서는 두 크기를 구분합니다.

| 구분             | 의미                                | 예시                   |
| ---------------- | ----------------------------------- | ---------------------- |
| 파일의 픽셀 크기 | 래스터 이미지에 들어 있는 픽셀 수   | 1200 × 800 이미지 픽셀 |
| CSS 표시 크기    | 레이아웃에서 이미지가 차지하는 크기 | 너비 400 CSS px        |

파일 자체의 픽셀 치수를 intrinsic pixel size라고 부르기도 합니다. 다만 브라우저 API의 <code>naturalWidth</code>는 밀도 보정된 CSS 픽셀 기준의 고유 너비이므로, 모든 상황에서 파일의 픽셀 너비와 같다고 보면 안 됩니다.

[MDN의 naturalWidth 설명](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/naturalWidth)

```html
<img
  src="/images/landscape-1200.jpg"
  alt="산과 호수가 보이는 풍경"
  width="1200"
  height="800"
  style="width: 400px; height: auto;"
>
```

이 코드에서 CSS는 표시 너비를 400px로 정합니다. 하지만 CSS로 작게 표시한다고 400픽셀짜리 파일을 다운로드하는 것은 아닙니다. <code>src</code>가 가리키는 1200픽셀 파일을 받아서 축소해 표시합니다.

즉, <b>화면에서 작게 보이게 하는 것과 작은 파일을 받게 하는 것은 별개의 작업</b>입니다.

## 3. DPR에 따른 이미지 해상도

CSS 픽셀은 화면의 물리 픽셀과 항상 일대일로 대응하지 않습니다. 이 관계를 이해할 때 사용하는 값이 DPR(Device Pixel Ratio)입니다. 브라우저에서는 <code>window.devicePixelRatio</code>로 확인할 수 있으며, 화면 환경이나 페이지 확대에 따라 달라질 수 있습니다.

[MDN의 devicePixelRatio 설명](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio)

같은 너비 400 CSS px의 이미지를 표시하더라도 DPR이 2라면 가로 방향으로 약 800개의 이미지 픽셀이 있어야 화면의 픽셀 밀도에 대응할 수 있습니다.

```txt
필요한 이미지 너비의 기준 ≈ CSS 표시 너비 × DPR

400 CSS px × DPR 1 = 400 이미지 픽셀
400 CSS px × DPR 2 = 800 이미지 픽셀
400 CSS px × DPR 3 = 1200 이미지 픽셀
```

여기서 계산한 값은 후보 선택을 이해하기 위한 기준입니다. 무조건 그 크기의 파일을 받아야 한다는 규칙은 아닙니다. 원본의 품질, 압축 수준, 네트워크 비용까지 고려하면 적절한 크기는 달라질 수 있습니다.

직접 계산한 크기에 맞춰 JavaScript로 주소를 바꿀 필요는 없습니다. HTML에는 브라우저에 선택지를 전달하는 방법이 있습니다.

## 4. srcset과 sizes를 통한 후보 선택

<code>srcset</code>의 <code>w</code> descriptor는 각 파일의 실제 픽셀 너비를 나타냅니다.

```html
srcset="
  /images/landscape-480.jpg 480w,
  /images/landscape-800.jpg 800w,
  /images/landscape-1200.jpg 1200w,
  /images/landscape-1600.jpg 1600w
"
```

<code>800w</code>는 “화면에 800px로 표시하라”가 아니라 “이 파일의 너비는 800 이미지 픽셀이다”라는 뜻입니다. 파일을 직접 리사이즈해 준비해야 하며, 숫자만 붙여서는 파일이 작아지지 않습니다.

<code>sizes</code>는 현재 레이아웃에서 이미지가 차지할 너비를 브라우저에 알려줍니다. 다음 예제는 뷰포트가 600px 이하이면 화면 너비 전체를, 그보다 크면 600px를 차지하는 이미지입니다.

```html
<style>
  body {
    margin: 0;
  }

  .article-image {
    display: block;
    width: 100vw;
    max-width: 600px;
    height: auto;
  }
</style>

<img
  class="article-image"
  src="/images/landscape-800.jpg"
  srcset="
    /images/landscape-480.jpg 480w,
    /images/landscape-800.jpg 800w,
    /images/landscape-1200.jpg 1200w,
    /images/landscape-1600.jpg 1600w
  "
  sizes="(max-width: 600px) 100vw, 600px"
  width="1200"
  height="800"
  alt="산과 호수가 보이는 풍경"
>
```

예제의 후보 파일은 모두 같은 구도와 3:2 비율로 준비했다고 가정합니다. <code>src</code>는 기본 이미지 주소이자 호환성을 위한 대체 경로입니다. <code>w</code> descriptor를 지원하는 브라우저는 이 예제에서 <code>srcset</code>과 <code>sizes</code>를 이용해 후보를 선택합니다.

<code>sizes</code>는 앞에서부터 조건을 평가하고 처음 맞는 항목을 사용합니다. 마지막 <code>600px</code>는 앞 조건에 해당하지 않을 때의 값입니다. <b>실제 레이아웃은 CSS가 만들고, <code>sizes</code>는 그 너비를 선택 과정에 전달합니다.</b> <code>sizes</code>만 바꿔도 화면의 이미지 크기가 바뀌지는 않습니다.

[HTML 표준의 반응형 이미지 설명](https://html.spec.whatwg.org/dev/images.html)

### 후보를 선택하는 과정을 숫자로 보면

위 예제에서 일반적인 밀도 기준으로 예상하면 다음과 같습니다.

| 뷰포트 너비 | sizes로 계산한 너비 | DPR | 목표 너비 | 예상 후보 |
| ----------- | ------------------- | --- | --------- | --------- |
| 400 CSS px  | 400 CSS px          | 1   | 400px     | 480w      |
| 400 CSS px  | 400 CSS px          | 2   | 800px     | 800w      |
| 400 CSS px  | 400 CSS px          | 3   | 1200px    | 1200w     |
| 1000 CSS px | 600 CSS px          | 2   | 1200px    | 1200w     |

이 표는 계산 예시이며 실제 다운로드 결과를 보장하지 않습니다. 브라우저는 네트워크 상태 등도 고려할 수 있고, 캐시나 이미 받은 이미지의 재사용 때문에 결과가 달라질 수 있습니다. 화면을 줄였다고 반드시 더 작은 파일을 새로 받는 것도 아닙니다.

<code>w</code> 후보를 쓰면서 일반적인 <code>sizes</code>를 생략하면 선택 계산에서 기본적으로 <code>100vw</code>가 사용됩니다. 실제로는 600px인 이미지를 더 넓게 표시한다고 판단하면 필요 이상으로 큰 후보를 받을 수 있습니다. 정확한 <code>sizes</code>가 중요한 이유입니다.

[HTML 표준의 sizes 규칙](https://html.spec.whatwg.org/dev/images.html#sizes-attributes)

## 5. loading과 fetchpriority의 역할

지금까지는 <b>어떤 파일을 받을지</b>를 살펴봤습니다. 다음으로는 <b>로딩 시점과 요청 우선순위</b>를 살펴봅니다.

<code>loading="lazy"</code>는 이미지가 뷰포트에 가까워질 때까지 로딩을 미룰 수 있게 합니다. 반드시 화면 안에 들어오는 순간에 시작하는 것은 아니며, 시작 거리는 브라우저와 환경에 따라 달라집니다. 처음 화면에서 멀리 떨어진 본문 이미지 등에 적합합니다. <code>loading="eager"</code>는 지연 로딩을 적용하지 않는 기본 동작입니다.

[web.dev의 브라우저 이미지 지연 로딩 가이드](https://web.dev/articles/browser-level-image-lazy-loading)

```html
<!-- 첫 화면 아래에 있는 본문 이미지 -->
<img
  src="/images/detail-800.jpg"
  alt="제품 측면의 연결 단자"
  width="800"
  height="600"
  loading="lazy"
  style="max-width: 100%; height: auto;"
>
```

반면 <code>fetchpriority</code>는 해당 이미지 요청의 상대적인 중요도를 전달하는 힌트입니다. <code>high</code>, <code>low</code>, <code>auto</code>를 사용할 수 있습니다. <code>eager</code>라고 해서 자동으로 최상위 우선순위가 되는 것은 아닙니다. <code>high</code> 역시 즉시 다운로드하거나 먼저 표시한다는 보장은 아닙니다.

[MDN의 fetchpriority 설명](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/fetchpriority)

```html
<!-- 첫 화면의 주요 이미지이며 LCP 후보인 경우 -->
<img
  src="/images/hero-1200.jpg"
  alt="가을 산길을 걷는 사람"
  width="1200"
  height="800"
  loading="eager"
  fetchpriority="high"
  style="display: block; width: 100%; height: auto;"
>
```

이 예제는 로딩 속성에 집중해 후보 목록을 생략했습니다. 실제 반응형 이미지라면 앞의 <code>srcset</code>, <code>sizes</code>도 함께 적용할 수 있습니다.

LCP(Largest Contentful Paint)는 뷰포트에서 가장 큰 이미지나 텍스트 블록 등 주요 콘텐츠가 표시되는 시점을 측정합니다. 첫 화면의 큰 이미지가 LCP 요소라면 지연 로딩이 표시 시점을 늦출 수 있습니다. 이런 이미지는 일찍 발견할 수 있게 하고, 필요하면 <code>fetchpriority="high"</code>로 중요도를 전달합니다. 모든 이미지에 <code>high</code>를 붙이기보다는 실제 LCP 요소를 측정해 적용합니다.

[web.dev의 LCP 최적화 가이드](https://web.dev/articles/optimize-lcp)

## 6. width와 height로 레이아웃 공간 확보하기

이미지 공간을 미리 확보하지 않으면 이미지가 표시되면서 아래 콘텐츠가 밀릴 수 있습니다. 브라우저가 이미지 공간을 미리 확보하지 못했다면 다운로드 후 크기가 드러나면서 레이아웃이 바뀔 수 있습니다.

CLS(Cumulative Layout Shift)는 이런 예기치 않은 레이아웃 이동을 측정합니다. 이를 줄이는 대표적인 방법이 이미지에 올바른 <code>width</code>와 <code>height</code>를 넣는 것입니다.

```html
<img
  src="/images/landscape-1200.jpg"
  alt="산과 호수가 보이는 풍경"
  width="1200"
  height="800"
  style="display: block; width: 100%; height: auto;"
>
```

이 속성은 CSS가 없을 때 기본 치수로도 쓰이지만, 여기서는 <b>다운로드 전에 3:2 비율을 알린다</b>는 점이 중요합니다. CSS로 정해진 너비가 600px라면 브라우저는 높이 400px의 공간을 계산할 수 있습니다. 반드시 화면에 1200 × 800px로 고정되는 것은 아닙니다.

속성의 비율은 실제 이미지와 맞춰야 합니다. 잘못된 비율을 주면 이미지 로드 후 비율이 정정되며 이동이 생길 수 있습니다. 서로 다른 비율의 이미지를 같은 틀에 넣는 디자인이라면 별도의 고정된 <code>aspect-ratio</code> 영역과 <code>object-fit</code> 등을 고려합니다.

[web.dev의 이미지와 CLS 설명](https://web.dev/articles/optimize-cls)

빠르게 다운로드하는 것과 공간을 미리 확보하는 것은 해결하는 문제가 다릅니다. 작은 파일도 공간이 없으면 레이아웃을 밀 수 있습니다.

## 7. 실제로 어떤 파일을 받았는지 확인하기

설정 후에는 브라우저 개발자 도구에서 확인합니다.

1. 원하는 뷰포트와 DPR을 설정하고, 캐시를 비활성화한 상태로 새로고침합니다.
2. Network 패널에서 이미지 요청 URL과 전송량, 요청 시점 및 소요 시간을 확인합니다.
3. Performance 패널에서 LCP 요소와 표시 시점, 레이아웃 이동을 확인합니다.

다음 코드는 위의 <code>.article-image</code> 예제에서 선택된 주소와 표시 너비를 확인하는 용도입니다.

```javascript
const image = document.querySelector(".article-image");

if (image instanceof HTMLImageElement) {
  console.table({
    selectedURL: image.currentSrc,
    displayWidthCSSPx: image.getBoundingClientRect().width,
    dpr: window.devicePixelRatio,
  });
}
```

이미지 선택이 끝난 뒤 실행합니다. <code>currentSrc</code>는 선택된 URL을 보여주며, 다운로드가 성공했다는 뜻까지는 아닙니다. 실제 요청은 Network 패널과 함께 확인합니다.

[MDN의 currentSrc 설명](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/currentSrc)

다운로드가 오래 걸리면 후보 크기와 전송량을 살펴봅니다. 다운로드는 끝났는데 늦게 보인다면 디코딩이나 메인 스레드 작업, 스타일에 따른 표시 지연 등을 조사합니다. 한쪽 수치만으로 원인을 단정하지 않는 것이 중요합니다.

## 핵심 요약

- 이미지는 발견, 후보 선택, 다운로드, 디코딩, 렌더링 과정을 거쳐 보입니다.
- 파일의 픽셀 크기와 CSS 표시 크기는 다릅니다. CSS로 줄여도 다운로드할 파일이 작아지지는 않습니다.
- 표시 너비 × DPR을 기준으로 필요한 픽셀 너비를 생각할 수 있습니다.
- <code>srcset</code>의 <code>w</code>는 파일 너비를, <code>sizes</code>는 레이아웃에서 예상하는 표시 너비를 전달합니다. 최종 선택은 브라우저가 합니다.
- <code>loading</code>은 지연 로딩 여부를, <code>fetchpriority</code>는 요청의 상대적인 중요도를 다룹니다. LCP 이미지는 지연 로딩을 피합니다.
- 올바른 <code>width</code>, <code>height</code> 비율로 공간을 미리 확보하면 이미지로 인한 CLS를 줄일 수 있습니다.
